# Evidence: the real Razorpay loop

`real_loop.json` is the unedited audit trail of one payment recovered end to end
on Razorpay test mode. Every step happened against Razorpay's real API, with
webhooks delivered over a public tunnel.

Nothing in it is simulated. Every other number in this repository is.

## What happened

| | |
|---|---|
| Case | `pay_TTiSk4zWggRdua` |
| Amount | ₹2,499 |
| Cause | `hard_decline` — confidence 1.0, deterministic |
| Action chosen | `method_switch_prompt` |
| Razorpay payment link | `plink_TTiTQCnaqNT3HK` |
| Idempotency key | `d5e5e9bd-ea12-4031-9e78-89ad30fbc5dc:method_switch_prompt:1` |

## Two details worth reading closely

**It chose `method_switch_prompt`, not a retry.** The cause was `hard_decline` — the issuer
refused the card. Retrying the same instrument gets refused again. Razorpay's own
published error taxonomy already encodes that; no model was trained to learn it,
and the deterministic lookup reached it at confidence 1.0.

**`matched by notes.recoup_case_id`.** A Razorpay payment link creates its *own*
order, lazily, at payment time — `payment_link.create` returns `order_id: None`.
So the recovering payment arrives on an order the original case has never seen.
Attribution matching only on order id, which is what this system originally did,
would have recorded this as an unrelated payment.

The distinction is not academic. An earlier run of this loop reported `RECOVERED`
while the payment link had silently failed to create, and the customer had paid
through the original checkout instead — the system credited itself with a
recovery it had done nothing to cause. `matched_by` exists so that failure mode is
visible in the trail rather than hidden behind a status field. See INCIDENTS.md.

## Reproducing it

```bash
make api          # in one terminal
make real-loop    # in another; it pauses twice for a human to pay
```

Requires Razorpay test keys in `.env` and a public tunnel pointed at
`/webhooks/razorpay`.
